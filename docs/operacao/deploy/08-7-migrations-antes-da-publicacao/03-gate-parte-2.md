e o índice `UX_tbwhatsapp_contato_TelefoneNormalizado`**, e **`tbwhatsapp_numero.WAT_FuncaoId` com a
FK `FK_tbwhatsapp_numero_tbfuncao`** (vínculo do número com a `tbfuncao`), e a tabela
**`tbwhatsapp_mensagem_reacao` com o índice único `UX_tbwhatsapp_mensagem_reacao_MensagemAutor`**
(Fase 8; sem o script Fase 9, o publish **aborta**). As credenciais vêm de
`PREFLIGHT_DB_SERVIDOR`, `PREFLIGHT_DB_BANCO`, `PREFLIGHT_DB_USUARIO` e `PREFLIGHT_DB_SENHA` (ou
parâmetros do script). Sem elas, o publish **aborta**; `-PularPreflightSchema` existe apenas para
uma emergência consciente. O `smoke.ps1` também passou a exigir **401** no login com usuário
fictício: **500 ali significa schema/código quebrado**, como no incidente de 2026-10-21 (build
`ee0930f` publicado sem `CARGO_ID`).

⚠️ **SQL Server não aceita `ON DELETE RESTRICT`.** O TSQL só admite `NO ACTION | CASCADE | SET NULL | SET DEFAULT` nessa cláusula; `RESTRICT` é palavra de outro dialeto e **aborta o `CREATE TABLE` com erro de sintaxe apontando a linha da constraint, não o `ON DELETE`** — o que manda o operador procurar o defeito no lugar errado. A primeira execução deste script falhou exatamente assim (`Mensagem 156, Nível 15, Estado 1`). `NO ACTION` é o padrão do SQL Server e equivale ao `RESTRICT` do padrão SQL.

Em compensação, o C# usa `DeleteBehavior.Restrict`, que é o valor certo no EF Core — a divergência entre o C# e o T-SQL é intencional e não é erro.

⚠️ **`deploy.ps1` não roda `Migrate()` nem `dotnet ef`.** Schema e binário podem divergir silenciosamente: aplique o script **antes** de publicar o binário que depende dele. Os scripts são idempotentes e podem ser reexecutados; ainda assim, faça backup antes de um script com `DROP`.

⚠️ **Não rode `dotnet ef migrations add` neste repositório.** O precedente: em 2026-10-11, ao tentar gerar a migration do módulo de Ideias, o EF produziu um `Up()` com operações de `tboportunidade`, `tblead` e `tbleadcontato` — entre elas **`DropColumn("DATA_ULTIMO_ACESSO", "tboperador")`**, que destruiria a coluna — porque o `AppDbContextModelSnapshot.cs` estava defasado (a migration `20261008090000_ComercialFunilProdutos` foi escrita à mão, sem `.Designer.cs`). A migration foi descartada e "o esquema do módulo vive só no script `.sql`". **Estado atual (2026-10-19):** a migration `20261019203821_TbDocDocumentos` (docs-api) também é escrita à mão e **sincronizou o snapshot com o modelo inteiro** — incluiu o funil comercial e as entidades de Ideias/Gestores que faltavam. A regra operacional permanece: as migrations deste projeto derivam de revisão manual (script idempotente aplicado antes do publish); se qualquer migration voltar a ser escrita à mão sem atualizar o snapshot, a revisão linha a linha volta a ser **obrigatória** para qualquer SQL gerado.
